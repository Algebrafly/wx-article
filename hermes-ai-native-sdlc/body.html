上周跟一个做平台的团队聊，他们说瓶颈已经不是"agent 会不会写代码"了。

是它写完之后，人要挨个 review、挨个点合并、挨个补上下文。一个人同时盯三个 agent，比自己写还累。

问题不在模型。在交接。

这篇拆两件事：AI native SDLC 里，多智能体到底怎么接力把流程往前推；以及市面上已经有哪些成型的产品和设计概念，哪些可以直接拿来用。

单 agent 再强，也只是一双手。流水线要跑起来，靠的是工位和传送带。

图 1 · 传统 SDLC 每一步都要人推；AI-native 把人挪到四个闸口

1

卡点不是模型，是交接

传统 SDLC 的每一步都靠人当传送带：需求评审完，人去通知开发；开发完，人去催测试；测试过了，人去点合并。

这套流程默认"人是不掉链子的"。可一旦换成 agent，掉链子的地方全暴露了：需求写在哪、设计改了几版、测试证据在哪个目录，没人说得清。

所以拆多智能体，第一动机不是并行提速，是职责隔离。

一个 agent 同时负责理解需求、做设计、写代码、写测试、判断质量，它一定会偷懒——因为它知道后面没人卡它。拆开之后，每个工位只做一件事，也只在同一个口径上被考核。

多智能体失败，绝大多数不是某个 agent 笨，而是交接处信息丢了。上下文一断，后面的 agent 就开始自由发挥。

这就引出一条硬规则：agent 之间不该靠聊天传话，要靠文件交接。

聊天记录是易失的、有歧义的、没法审计的。而一份落盘的 spec.md、tasks.yaml、evidence.json，可以被读、被 diff、被回滚、被拿去当证据。

2

市面上已经跑通的四条路线

先看真实产品。这个赛道在 2026 年已经不算早期了，能拿出来讲的至少有五家。

Devin：从"一个工程师"到"一群工程师"

Cognition 在 2024 年 3 月把 Devin 推出来，第一次让"AI 软件工程师"这个词变得具体：一个沙箱云主机，里面有浏览器、终端、编辑器，从 Slack、Jira 或网页派活，它自己规划、写码、跑测试、提 PR。

到 2026 年，它的重点已经变成编排：一个 orchestrator 负责拆范围、盯进度、处理冲突，底下若干 Devin 实例在隔离 VM 里干活。

GitHub Copilot：把流程写成 agent 文件

GitHub 的路子更"进仓库"：在 .github/agents/ 下放一个 Markdown 文件，加上 YAML front matter，就把团队的做事方式固化成一个专门 agent。code review、性能优化、无障碍检查都能各配一个。

配套的 Spec Kit 走的是规格驱动：先写清"要什么"，再让 agent 拆"怎么做"。Levi Strauss 甚至在这个平台上搭了 17 个 agent 跑完整条 SDLC，用 MCP 连上 Jira、Confluence 和监控。

Factory 与 Warp：两条软件工厂路线

Factory 卖的是一个托管好的装配线：Droid 是执行体，底下有模型路由，在 Claude、Gemini、GPT 之间按任务挑；上层是 Missions、Automations 和自主等级。

Warp 反过来，把工厂本身当基础设施开放出来：你用自己的模型和运行环境，把 agent 舰队挂到 SDLC 上，由 issue、Slack 消息或定时任务触发，从分诊一路跑到可合并的 PR，再用 eval 持续证明它没退步。

Kiro 与 Claude Code：规格与子 agent

Amazon 的 Kiro 把规格驱动做进了 IDE：requirements.md、design.md、tasks.md 三件套，验收标准用 EARS 语法写，逼着"想要"变成"可测"。

Anthropic 则把 subagent 和 agent teams 做成了原生能力，一个会话里可以拉起几十上百个并行子 agent，最后自己验证再汇报。

图 2 · 横轴看覆盖多长，纵轴看能不能自己改

把这六家放到一张图上，其实只有两个变量：覆盖多长，和能不能自己改。

封闭工厂开箱即用，但流程是别人的，你想加一道自己公司的合规闸口，得等厂商排期。开放基建什么都能改，代价是你要自己养一套 eval 和可观测。

中间地带最难：用别人封装好的流程，改不动；全自己拼，维护不起。

3

三个已经被验证的设计概念

产品之外，概念层有三样东西已经收敛了。不管用哪家工具，这三样都绕不开。

一、规格驱动：spec → plan → tasks → code

GitHub、AWS、Anthropic、Cursor、Google 现在都在推同一个形状：先把规格写清楚，再拆计划，再拆任务，最后才写代码。

社区实践下来最舒服的粒度是一页到三页的紧凑规格：用户故事、EARS 验收标准、明确的"不做什么"，以及阶段之间的人工评审点。

EARS 的价值在于句式固定：WHEN 条件 THE SYSTEM SHALL 行为。一句话一个断言，天然可测。写不出这个句式，说明需求还没想清楚。

二、仓库宪法：AGENTS.md

在仓库根放一份 AGENTS.md，所有 agent 读同一份规则：怎么跑测试、什么不许改、提交信息怎么写、哪些目录是雷区。

它解决的是"每个 agent 都要重新教育一遍"的问题。规则进了版本库，就能 review、能回滚、能追责。

三、两条协议：MCP 管工具，A2A 管协作

MCP 把 Jira、Confluence、监控、数据库这些系统和数据接成 agent 能调的工具；A2A 让 agent 之间能互相发现、委派任务、回传结果。

前者解决"agent 看不见外部世界"，后者解决"agent 之间怎么搭班"。

概念可以借，但落地时真正决定成败的，是工件格式是否稳定。

4

把 SDLC 拆成八个工位

落到具体设计，我倾向于把人这样的"全能角色"拆成八个工位，每个工位一个 agent。

triage 负责把原始诉求变成可复现的 issue；spec 负责把它写成带 EARS 验收标准的规格；architect 出设计和取舍记录；planner 拆任务和依赖；coder 出最小 diff；verifier 跑测试、扫描、基准，攒证据；reviewer 对照证据挑刺；release 备灰度和回滚。

图 3 · 每个工位只认上一个工位落盘的文件

每个工位只做一件事，只吃上一手的文件，只吐自己的文件。上游不合格，直接打回，不往下传。

这样做有两个直接好处。

一是可替换。今天用 A 模型写 spec，明天换 B，只要 spec.md 的格式不变，下游完全无感。

二是可审计。出了事故，能顺着一串文件往回倒：谁的假设错了，在哪一步丢的。

这也是为什么我坚持"文件而不是消息"。消息只能回答"当时说了什么"，文件才能回答"当时依据什么做的决定"。

5

人只保留四个闸口

如果每个工位都要人点头，那只是把流水线换了个地方堵。人应该出现在不可逆的节点上。

图 4 · 四道闸口，越往后拒绝成本越高

立项：这件事值不值得做，有没有更便宜的解法。三十秒就能判断，错了成本也最低。

规格冻结：验收标准能不能测，边界写清楚没有。这一步放行之后，下游就开始花钱了。

合并：diff 和证据对不对得上，有没有偷偷扩范围。十五分钟，看的是证据链，不是代码风格。

上线：回滚预案是什么，今晚谁值班。五分钟，只确认这两件。

其余时间，agent 自己推进。卡住了怎么办？定一条升级规则：同一个阻塞超过三十分钟没解开，自动发卡片 @ 对应负责人，并附上已经试过的三条路。

注意这条规则的重点不是"叫人"，是"附上已经试过什么"。没有上下文的求助，等于把问题原样甩回给人。

闸口的价值不在"批准"，在于让拒绝发生在成本最低的那一刻。

6

用 Hermes 拼一套能跑的

思路清楚了，剩下的就是把八个工位变成一个可执行的编排。用 Hermes 的话，四样东西够用：Profile 做隔离，SOUL.md 定人设，Skill 定动作，A2A 总线做交接。

目录先摆成这样：

sdlc/
  agents/
    triage/SOUL.md
    spec/SOUL.md
    architect/SOUL.md
    planner/SOUL.md
    coder/SOUL.md
    verifier/SOUL.md
    reviewer/SOUL.md
    release/SOUL.md
  skills/
    handoff/SKILL.md
    escalate/SKILL.md
  pipeline.yaml
  AGENTS.md

编排写在 pipeline.yaml 里。关键是每个工位声明三件事：吃什么、吐什么、什么条件下才放行。

stages:
  - id: spec
    agent: spec
    in: [issue.md]
    out: [spec.md]
    gate: human
    pass_when:
      - every_acceptance_criteria_is_testable
      - out_of_scope_is_explicit
  - id: coder
    agent: coder
    in: [spec.md, design.md, tasks.yaml]
    out: [pr.patch, self_test.log]
    gate: auto
    pass_when:
      - ci_green
      - diff_lines_under_400

人设要写窄。spec agent 的 SOUL.md 不该说"你是一个资深产品经理"，而该说清楚它必须产出什么、什么情况下必须停下来问。

# spec agent

你只产出一份 spec.md，不写代码。
每条验收标准必须是 EARS 句式：
  WHEN <触发> THE SYSTEM SHALL <可观测行为>
写不出可测行为时，标 STATUS: BLOCKED，
列出你需要人回答的三个问题，不要猜。
必须包含 Out of Scope 一节，至少两条。

"不要猜"这三个字值很多钱。多智能体系统里最贵的错误，是 agent 用一段编造的假设，把整条流水线顺利地推到了上线。

交接用 A2A 总线，但要带版本。下游 agent 收到的不是"spec 好了"这句话，而是 spec.md 的内容加一个 hash。上游改过，下游自动失效重跑。

人工闸口用审批卡实现：agent 发一张带按钮的卡片，人点了"通过"，回调把流程往前推一格；点了"打回"，必须填一句原因，这句话会作为新输入进入上一工位。

没有回传理由的"打回"，等于让 agent 重新掷一次骰子。

7

群消息、边界和几个坑

流程状态要推到项目群，但只推三种：要人决策的、卡住要人的、做完要知会的。

图 5 · 一个决策一张卡，一句话说清要人做什么

格式统一成三段：一句判断、最多三行事实、一个明确请求。@ 到具体的人，不 @ 全员。

最后说几个真会踩的坑。

上下文腐烂

流程跑得越长，spec 越可能被悄悄改过，下游却还拿着旧版本干活。解法只有一个：所有工件带版本和 hash，上游一变，下游强制重跑。

agent 互相恭维

让一个 agent 去评审另一个 agent，很容易一路放行，尤其是同一个模型。别让 reviewer 发表意见，让它对照证据做判定：测试过没过、覆盖率够不够、扫描有没有高危。机器只认证据。

并行冲突

多个 agent 同时改同一个模块，合并时一定打架。按模块切 owner，每个 agent 一个分支或 worktree，谁的模块谁负责 rebase。

没有 eval 就没有改进

每个工位都得有自己的通过率和返工率。spec 被打回几次、coder 的 PR 一次过比例多少、verifier 漏掉的缺陷有几个。没有这些数，你只是在感觉它变好了。

还有个软性提醒：别把 agent 数量当 KPI。八个各司其职的工位，比三十个抢活干的 agent 有用得多。

说到底，AI native 不是"无人"，是把人的注意力从每一步挪到关键几步。

流水线自己会跑，人负责在不可逆的地方停一下。
