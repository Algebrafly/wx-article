项目做完，复盘的时候常听到一句话：范围一直没控制住。

再问细一点，通常能问出三种情况。

一种是蔓延：客户随口提的、老板临时加的、销售答应下来的，一条条堆进去，谁也没算过总共多少个。另一种是镀金：团队自己觉得「顺手做了更好」，加了一堆没人要的功能。还有一种是说不清：范围说明书里写的是「优化用户体验」，验收时两边理解差了十万八千里。

三种情况，根因是同一个：范围没有被写成可判定的事实。

范围失控从来不是态度问题，是记录问题。

上一篇搭了项目管理的骨架，这一篇把「范围管理」这一个领域拆到底：六个过程各自的输入、技术、输出，六份文档的字段，文档怎么进知识库变成组织过程资产，以及四种发到项目群的消息格式。

最后会给出这个 SKILL 的目录结构和关键配置，能直接照着搭。

1

六个过程，其实是一条传送带

范围管理的六个过程，教科书上是分开讲的，看起来像六件独立的事。放到真实项目里，它们首尾相接，是一条传送带。

规划范围管理 定规则。怎么定义范围、谁来验收、变更走什么流程。这一步产出的两份计划，后面每一步都要引用。

收集需求 从干系人那里把需求捞上来，编号、归类、定优先级。产出需求文件和需求跟踪矩阵，后者是整条链最关键的锚点。

定义范围 把需求收敛成一份边界清晰的范围说明书。这一份文档的核心不是写了什么，是写了「不做什么」。

创建 WBS 把范围拆成可估算、可分配、可验收的工作包。拆不下去的，说明范围还没想清楚。

确认范围 拿可交付成果去换签字。注意这是「确认」，不是「控制」——它面向客户，控制面向内部。

控制范围 持续监测有没有跑偏，跑偏了就提变更。这一步是全年无休的，不是阶段末才做。

传送带的关键在于：每一环的输出，都是下一环的输入。需求文件没编号，跟踪矩阵就对不上；跟踪矩阵对不上，验收时就没法证明「这个需求实现了」；没法证明，控制范围就只剩吵架。

所以 AI 介入的切入点不是「帮我写一份范围说明书」，而是守住这条链上的每一环都不掉东西。

2

输入从哪来：把 ITTO 翻译成接口

教科书里的输入是一串名词：项目章程、需求文件、事业环境因素、组织过程资产。听起来都很抽象。

落到系统里，它们其实是五个可以接的源：

项目平台 禅道、Jira、PingCode 里的需求单、任务、缺陷。这是需求文件和跟踪矩阵的主要来源。

文档库 企微文档、飞书文档、Confluence 里的 PRD、会议纪要、合同附件。范围说明书和章程的原料在这里。

代码仓库 提交记录和 MR 描述。用来反查「这个需求到底做了没有」，以及实际改动范围有多大。

IM 群消息 客户群里随口提的、老板转发的、销售答应的。范围蔓延的 80% 藏在这里，这是最容易被忽略的输入源。

知识库 本项目和其他项目的历史范围文档。这就是「组织过程资产」，下一篇会专门讲怎么用。

五个源里，前四个是事实来源，第五个是经验来源。事实告诉你「现在是什么样」，经验告诉你「以前这样做出过什么问题」。

接入方式都是只读。项目平台用 API token，文档库用只读应用授权，代码仓用只读 deploy key，IM 群用机器人读消息权限。一个写权限都不要给——范围管理的第一原则是不擅自改变事实。

3

技术环节：AI 该做什么，不该做什么

ITTO 里的「技术」叫工具与技术，比如访谈、引导式研讨会、分解、偏差分析。这些原本都是人的动作。

AI 介入之后，有些动作被替代了，有些被放大了，还有些必须保留给人。分清楚这三类，比写多少提示词都重要。

能替代的：重复的搬运和比对

需求散在五个地方，人工整理一遍要半天。AI 三分钟能拉齐、去重、编号、补全字段。这类活它做得又快又稳，而且不会因为下午四点半要下班就漏掉两条。

能放大的：人做不完的穷举

「帮我列出这个功能所有可能的异常场景」——人能想五个，它能想三十个。然后人从三十个里挑出真正相关的八个。

这就是正确的分工：它负责把候选集做全，你负责做取舍。

不能替代的：跟人确认边界

范围管理的核心动作是谈判：这个需求做不做、什么时候做、做到什么程度。谈判的对象是人，筹码是资源和时间，后果由人承担。

AI 能做的是把谈判需要的材料准备好：这个变更影响几天、历史上类似变更多花多少、不做的话谁会受影响。它不能替你在会上说「这个我们不做」。

还有一条更微妙的：它不能替你判断「客户真正想要什么」。客户说「要快」，可能是要性能，也可能是不想等审批。这种弦外之音，只有坐在对面的人能听出来。

4

六份文档，六套固定字段

这是整套 SKILL 里最实在的部分。模板不是格式美观问题，是让「填不出来的字段」暴露「还没想清楚的地方」。

字段一旦固定，AI 就能做三件事：自动填充已知的、标红未知的、针对未知的生成追问清单。

范围管理计划

四个字段：范围定义方法、验收标准与流程、变更审批链路、WBS 分解层级。这份文档一个项目只写一次，但后面每一步都要引用，所以必须基线化。

需求文件

五个字段：REQ-ID、来源干系人、优先级加理由、验收条件、状态。其中验收条件必须可测——「响应要快」不是验收条件，「P95 小于 200ms」才是。

需求跟踪矩阵

这是整条链的脊柱。一行一个需求，横向串起「业务目标 → 设计 → 代码提交 → 测试用例 → 验收状态」。

它有三个用途：审计时证明每个需求都有来源和去向；验收时证明每个需求都有测试；控制范围时发现「有代码提交但没需求单」的野生功能。

项目范围说明书

五个字段：项目目标与成功标准、可交付成果清单、除外责任、假设条件、约束。第三项最容易被跳过，也最能救命。

「除外责任」要写得具体：不含历史数据迁移、不含多语言、不含移动端适配。写「不包含其他功能」等于没写。

WBS 与 WBS 词典

四个字段：WBS 编码、工作包负责人、工期与成本估算、验收标准。编码规则用 1.2.3 这种层级式，后面所有任务、缺陷、变更都挂在这个编码下。

拆到工作包的标准是：能估算、能分配、能验收。三条里缺一条，说明还得往下拆。

验收单与变更单

四个字段：交付物与验收结论、偏差说明、变更影响、签字人与时间。验收单只有「通过」「有条件通过」「不通过」三种结论，别搞第四种。

变更单的影响必须量化：范围加了多少、进度加几天、成本加几人日、有没有连带风险。写「影响较大」的变更单，等于没评估。

5

控制范围：三道判定抓蔓延

「控制范围」这四个字听起来很虚，落到代码上其实是三个具体的判断，每天跑一次。

第一道：基线比对

拿当前需求清单和基线版本做 diff。新增的、删除的、描述被改过的，全部列出来，逐条问一句「这个走变更了吗」。

注意要对比描述文本，不只是标题。「支持导出」改成「支持导出 PDF/Excel/CSV」，标题没变，工作量翻倍，这是最常见的隐性蔓延。

第二道：代码反查

扫最近合并的 MR，看提交信息里有没有关联需求单。没有关联的，要么是技术债，要么就是野生功能——没人提需求，团队自己做的。

野生功能不一定是坏事，但必须被记录。判定方式是让它回答一句：这个改动对应哪个 REQ-ID？答不上来，就进「待确认」清单。

第三道：语义扫描

扫 IM 群和会议纪要，找「能不能再加一个」「顺便把…也做了」「客户说还要」这类句式。命中的句子连上下文一起提出来，让 PM 判断是不是新需求。

这一道的误报率最高，但也最有价值。因为前两道只能发现「已经进了系统」的蔓延，第三道发现的是还在人嘴上飘着的蔓延。

三道的结果汇总成一张「范围偏差表」，每天推给 PM。有就推，没有就静默——这点很重要，天天推「今日无异常」，两周后这个群就会被静音。

确认范围这边反而简单：验收单必须对着 RTM 逐条过。哪条需求没有测试用例、哪条用例没有执行记录、哪条执行失败但状态写了通过，三个问题一查，验收质量就出来了。

6

组织过程资产：文档进知识库才算数

文档写完放共享盘，这是绝大多数团队的做法。结果是：写的时候认真，写完没人看，下个项目从零开始。

组织过程资产的价值不在「存了多少」，在「被检索到多少次」。所以归档不是复制粘贴，是加工成可检索的结构。

关键动作是入库前加一层 front-matter：

---
doc_id: pay-platform/scope-statement/v3
doc_type: scope_statement  # 六种类型之一
project: pay-platform
version: 3
status: baselined  # draft / baselined / superseded
baseline_at: 2026-11-06
owner: zhangming
stakeholders: [pay, finance, risk]
related: [REQ-012, REQ-018]
supersedes: v2
---

三个字段最关键。doc_type 决定它怎么被检索，status 决定它可不可信，related 决定它能不能和其他文档串起来。

状态机只有三种：draft 起草中、baselined 已基线、superseded 已作废。基线之后任何改动都必须走变更单，生成新版本，老版本标 superseded 但永不删除。

入库之后，四类场景会真的用上它：

· 新项目立项 找相似范围的历史项目，直接复用可交付成果清单

· 需求评审 查同类需求的验收条件和历史上的反例

· 变更评估 看以往同类变更的实际影响工时，别拍脑袋估

· 季度复盘 统计各项目的范围蔓延率，定位根因

第三类特别值钱。人工评估变更影响，通常往少了估——因为没人愿意说自己要加五天。但历史数据不会撒谎：过去十次「增加导出格式」的变更，平均实际花 3.2 人日。这个数字摆出来，评估就有锚了。

还有一个容易漏的：把「被拒绝的需求」也归档。哪些需求提过但没做、为什么不做，这些比做了的更有参考价值。半年后同样的需求再提一次，能立刻翻出当时的拒绝理由。

7

群消息：四种语气，一个结构

范围管理会产生四类事件，发到项目群里的语气完全不同。但结构是统一的：一句话标题 + 最多三行事实 + 一个明确请求。

范围预警

每天早上一跑，检测到未走变更的新需求就发。写清楚需求编号、一句话内容、预估工作量，最后 @ 具体的人并要求今天内确认。

关键是@ 到人，不 @ 全员。@ 全员的预警，第一次有效，第三次就没人看了。

变更审批

变更单创建时发。三段：变了什么、影响多少、什么时候截止。影响必须量化到进度和成本两栏，缺一栏就不发。

加一句超时处理规则，比如「超时自动挂起，进入下个迭代重评」。没有超时规则的审批，平均会拖五天。

验收通过

验收单签署后发。这条是唯一的好消息，别省略。团队需要看到「做完的事被确认了」，这是范围管理里少有的正反馈。

写清验收方式、偏差、验收人。有偏差的也照实写，别美化——验收单是要进知识库的，粉饰过的记录半年后会害到人。

范围健康度

每周五发一次。一个分数、三个指标（蔓延率、镀金项、变更次数）、一条根因、一个下周动作。

分数怎么算不重要，重要的是口径固定、连续可比。这周 78 分，上周 85 分，人自然会问「为什么掉了」。这一问就是复盘的开始。

前三类是事件驱动，要快；第四类是定时汇总，要准。别把汇总做成实时——每天发一次健康度，就变成噪音了。

8

SKILL 怎么组织

最后落到文件。一个 scope-manager 技能，目录结构大概是这样：

skills/scope-manager/
├─ SKILL.md          # 触发条件 + 六个过程的动作
├─ templates/
│  ├─ scope-plan.md
│  ├─ requirements.md
│  ├─ rtm.md
│  ├─ scope-statement.md
│  ├─ wbs-dict.md
│  └─ acceptance-change.md
├─ queries/
│  ├─ baseline_diff.sql  # 基线比对
│  ├─ orphan_commit.sql # 野生功能
│  └─ rtm_coverage.sql   # 需求覆盖
└─ render/
   ├─ warn.py          # 预警
   ├─ change.py        # 变更审批
   ├─ accept.py        # 验收
   └─ health.py        # 健康度

SKILL.md 不写「你是范围管理专家」这种废话，只写三件事：什么情况下触发、每个过程调哪个模板和查询、哪些动作必须停下来问人。

最后一条最重要。要明确列出「停止点」：发现新需求但不确定是否纳管、变更影响无法量化、验收结论存在争议——遇到这三种，停止自动流程，转人工。

三个定时任务挂在 cron 里就够：

· 每天 09:00 跑三道判定，有偏差就发预警

· 每周五 17:30 生成范围健康度，顺带把本周新文档归档

· 每月 1 日 做一次全量基线对账，把漂移的文档拉回来

范围管理不需要高频运行。它的价值在于稳定、可追溯，不在于秒级响应。

把范围写成事实，把事实存进知识库，把变化推到群里 —— 顺序不能颠倒。
