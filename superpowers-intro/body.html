从一句话到一次合并，中间要过的七道关。

今天想聊的是 Superpowers，一套专门给编程智能体的开发方法论，作者是 Jesse Vincent，MIT 协议开源，Claude Code、Codex、Cursor、Gemini CLI 这几种主流的都能装。

它有个地方很不一样。绝大多数插件想的是怎么给智能体加能力，它想的是怎么给智能体上纪律。

01

它管的不是能力，是纪律

装上之后，最先变化的是开头。

你说帮我做个什么，它不会立刻打开编辑器。它会先退一步，反问你到底想解决什么。等把你的需求问清楚了，它把设计一小段一小段摆给你看，等你点头。点完头才去写计划，写完计划才动代码。

听起来只是慢了一点点，但这个顺序本身就是它全部的价值。

这套东西由二十来个技能组成，中间第 4 到第 6 步会单独展开讲。

它为什么能做到自动接管，是因为每个技能的描述里都写死了它什么时候必须上场。负责总纲的那个技能里有句原话，我照抄：只要你觉得某个技能有哪怕 1% 的可能适用，就必须调用它。

而且它不是只对智能体狠。它还立了一条优先级：你写在 CLAUDE.md 里的明确要求 > 这套技能 > 系统的默认行为。你的话永远最大，哪怕你说的是别用 TDD。

02

装它，三行都不用到

Claude Code 已经把它收进了官方插件市场，一行就够。

/plugin install superpowers@claude-plugins-official

如果你习惯用作者自己的市场，把上面那条换成这两行。

/plugin marketplace add obra/superpowers-marketplace
/plugin install superpowers@superpowers-marketplace

换别的智能体也不麻烦。Gemini CLI 是扩充，Cursor 在对话框里加插件，Codex 走它自己的插件市场。

gemini extensions install https://github.com/obra/superpowers

装完不用记命令，也不用背技能名。它会在该出场的时候自己出来。

03

示例一，动手之前先把话问清楚

第一个技能叫 brainstorming，管的是需求。它的规矩是整个体系里最硬的一条：在把设计摆出来、并且被用户点头之前，不许调用任何实现类技能，不许写任何代码，不许搭任何脚手架。

它问问题的方式也很克制。一次只问一个，能出选择题就出选择题，绝不一口气甩你八个问题让你自己消化。

我特别喜欢它提前堵的一个洞。它专门写了一段，说别拿「这个太简单了，不需要设计」当借口。一个待办清单、一个工具函数、改一行配置，全都要走一遍。设计可以短到几句话，但必须摆出来让你确认。

理由写得很实在。越是简单的项目，越是那些没被审视过的假设在浪费工时。

最后它会把确认过的设计写成一份文档，存进仓库、提交，然后请你自己再读一遍。你说行，才进下一步。

还有一个细节值得说。它要求先给你 2 到 3 个方案，讲清各自的取舍，并且先讲它自己推荐的那个和理由。不是给你一堆选项让你自己想。

让智能体替你收敛选项，而不是把选择的负担推给你，这一条很多工具都做不到。

04

示例二，把计划细到能照着抄

设计通过了，下一步是 writing-plans。

它写计划的时候，假定的读者是一个热情、品味一般、对项目毫无了解、而且天生不爱写测试的初级工程师。所以每一句话都得写死。

粒度是这样切的，一个步骤一个动作，控制在两三分钟。写一个失败的测试，算一步。跑一遍确认它失败，算一步。写最少的代码让它通过，算一步。再跑一遍确认通过，算一步。提交，又算一步。

而且它明令禁止占位符。这些东西被它定义为计划失败，一个都不许出现。计划长这样：

- [ ] 写失败的测试
- [ ] 跑一遍，确认它以预期原因失败
- [ ] 写最少实现
- [ ] 跑一遍，确认通过
- [ ] 提交

对应文件路径要写全，代码要贴完整，命令要带上预期输出。不许写「加上适当的错误处理」，不许写「测试同上」，也不许写「你自己翻译一下」。

写完之后它自己会再审一遍，问三个问题：设计里的需求是不是每条都有对应任务，有没有残留的占位符，前一个任务里叫 clearLayers 的函数到了后面是不是还叫这个名字。

一份好计划的标准，是把判断留在写计划的时候，让执行的人只需要照着做。

05

示例三，没看见测试红过就不许写实现

轮到动手了，先上场的是 TDD 技能。它的铁律只有一句：

没有任何一行生产代码，
是在一个失败的测试之前写下的。

循环本身大家都会背。

红绿重构，外加它自带的铁律。

最能看出性格的是它对违规的处理。如果你先写了实现，再回头补测试，它要求你把那段代码删掉，从头来。

不留作参考，不边写测试边把它改成能过的样子，甚至不许回头看。删就是删，实现从测试里重新长出来。

这么偏执的原因它写得明明白白。测试写在代码之后，它一上来就是绿的。而一上来就绿的测试，什么都证明不了。

你亲眼看着它红过，才知道它真的在测东西，而不是在给你鼓掌。

06

示例四，没找到根因就不许动手

出 bug 的时候，用的是 systematic-debugging。它的铁律同样只有一句：没走完第一阶段，不许提出任何修复方案。

四个阶段，以及一条很硬的止损线。

它点名了几种最该用这套的场景，我读的时候觉得它很懂人。越是着急的时候越要用，越是看着像「就一行的小问题」越要用，越是已经试了好几个修法的时候越要用。

它还给了一组很有说服力的经验数字。按流程走，十几分钟到半小时修好，一次到位率大概九成半。随手乱改，两三个小时还在原地打转，一次到位率四成。

我最服的是那条止损线。同一个问题修到第三次还没好，停下来，别再修了，去质疑架构。

它的判断是，连续三次修不好，通常不是你假设错了，是架构本身有问题。修一次冒出一个新问题，换个地方又冒一个，这就是信号。这时候该跟人讨论的是要不要重构，不是再试第四次。

07

它最狠的地方，是把借口先堵死

这部分我觉得是整套东西里最值得偷师的。

几乎每个技能里都躺着一张对照表，左边写成你可能会有的念头，右边写现实。

写规则的人和用规则的人，都清楚自己会怎么偷懒。

还有一个技能专门管收尾，叫 verification-before-completion。它的铁律是，没有当场跑出来的验证证据，不许说完成。

它对措辞的要求细到有点好笑。只要开始出现「应该能行了」「大概没问题」「我很有把握」，就说明在没有证据的情况下宣称成功。测试通过不能靠上一次的结果，构建成功不能靠编辑器没报错，子智能体说做完了也不能直接信，得去看 diff。

说白了，这套东西真正的对手不是 bug，是你我都有的那种差不多就行了。

当然，也有人会嫌它啰嗦。它确实会让你多等几步，多回答几个问题，多写几遍测试。

但它把一件很难自动化的事做成了纪律：让智能体在动手之前先想清楚，在说好了之前先验证过。

能力决定它能写多快，纪律决定你敢不敢用。
