上周 DeepSeek 把 dsh-superagent-prototype 开源了。12 天，22k star。

这个项目和之前聊的 DeerFlow 很不一样。DeerFlow 给你的是一套能直接跑起来的 harness——开箱即用的 sub-agent、memory、sandbox、middleware。dsh-superagent 反过来，它给你的是一份设计。

作者自己说：这是一个 research prototype，工程里大量代码是 coding agent 写的，style 可能不一致。它的价值不在代码质量，而在那份编号文档——从 000 到 007，每一篇只依赖前面的知识，完整还原了他们对"super agent"的全部思考。

读完这八篇文档，我想聊三个我觉得最有意思的东西：注意力经济学、域模型的极简主义，以及 Ticket 状态机。这三样加起来，就是他们对"agent 怎么才算一个合格的团队成员"的回答。

1

注意力经济学：agent 是团队成员，不是机器人

dsh-superagent 的 000 号文档只有 40 行，核心观点一句话：

 

Take as little human attention as possible,
and give as much value as possible.

 

这不是一句 slogan。它是整个系统的评价标准。

dsh-superagent 把"注意力成本"放到了设计的最高层：一条系统通知、一个设置项、panel 里的一个数字、甚至文档里的一段话——每个东西都在消耗同事的注意力。它必须给回来更多价值，否则就被删除。

图 1 · agent 约束和设计约束都围绕"注意力"展开

这个视角把 agent 从"一个自动执行任务的工具"抬到了"团队成员"的位置。一个团队成员的行为准则是什么？

只在被 ask 或有 written rule 时才行动。没人 ask、没有 team 写下来的规则，它就不该动。哪怕它看到一个明显的 bug。主动做事的权限需要团队先把规则写出来，而且第一次执行走"只记录不做事"模式——先看它会做什么，对了再放开。

确认一次、完成一次、回答一次。agent 确认"收到，我去做 X"之后就静默工作。完成了汇报结果。卡住了报告阻塞。中间不刷屏。

按 impact 停，不按 effort 停。agent 做了一个小改动，产出一个可 review 的结果就停。它发现需要设计决策，停下来问清楚。它不自己猜。它不绕过边界只为避免发问。

对应的设计约束也三条：Few concepts, few settings（业务需求变成属性或 prompt，不是新概念）、Panel 只展示需要人的部分（健康状态不占空间）、文档按顺序读。

最后一条特别狠："Mass pull requests、broadcast messages、busywork cost the team more than they give." agent 能做更多，不代表它就该做更多。

2

域模型：七个概念，零冗余

001 号文档最精彩的地方不在七个概念本身，在那一张 Rejected concepts 表。它列了 11 个被拒绝的概念和拒绝理由。看完你就懂了：dsh-superagent 的极简不是因为没想到，是因为刻意砍掉了。

图 2 · Source → Trigger → Thread → Eval → Ticket → Executor

七个核心概念里最值得聊的是 Thread 和 Mandate。

Thread：Eval 的串行边界

Thread 是按时间顺序排列的 Trigger 流——GitHub 上同一个 PR 的评论、同一个 issue 的更新、Feishu 同一个话题下的消息，Source 决定哪些 Trigger 属于同一个 Thread。Thread 保证同一时刻最多一个 Eval 在跑，后来的 Trigger 会被合并进下一批次。

一个 Thread 可以同时挂多个 Ticket。这是他们拒绝掉"一个 Thread 一个 Ticket"的原因——同一个 PR 上，可能同时有"修复 lint 警告"和"添加新功能"两件独立工作。

Mandate：谁授权 agent 做什么

Mandate 是 Eval 产出的授权证书。它只记录四件事：Policy version、scope（允许做到什么范围）、strength（explicit 明确 / inferred 推断）、sender identity。Immutable。

Agent 不能自己扩大 scope。它看到 Mandate 的 scope 不够时，只能停下来问人。这是他们砍掉"append to Ticket"的原因——追加授权必须走新 Eval，不能偷偷加。

被拒绝的 11 个概念里，有几个特别说明问题：

Principal / Membership / 跨 Source 身份映射：拒绝。一个人是 Trigger 里的 metadata；allowed list 是 Policy 每个 Source 各自维护的 part；跨 Source 的身份对应关系是 agent 读 prompt 时的知识，不是域模型的概念。

Eval 的 delayed trigger / waiting / revoked 状态：拒绝。需要等待的条件是 Source 的事，不是 Eval 的事；Eval 超时就把 Triggers 重排或判 unavailable。

Ticket state 跟随 Executor Session：拒绝。Executor 可以被 handoff、多个 Executor 接力跑完同一个 Ticket，所以 Ticket 自己定义状态。

每次读到这种拒绝理由，都觉得这是真正见过生产的团队。不是为了炫技而砍概念，是见过这些概念长出来之后会让系统变复杂。

3

两条授权路径：Eval 和 Subscription

dsh-superagent 里有一条最重要的规则：只有 Eval 能产生新授权。其他路径只能给 Ticket 加上下文。

图 3 · Eval 两层判定；Subscription 只是上下文扇入

Eval 分两层：Gate（第一层，确定性）和 Assessment（第二层，模型判断）。

Gate 是硬规则。消息是不是 mention / direct？发消息的人在不在 allowed list？这条 Source 的 admission table 怎么写的？是不是 bot？Gate 直接过滤掉不该进 Eval 的东西。

Assessment 是模型判断。它拿到 Trigger 批次 + Thread 快照 + Thread 上所有 Ticket（包括 ended）+ 当前 Policy，输出一个 Decision：accept（接单）、stop（停止）、ignore（忽略）、unavailable（未完成，重排 Trigger）。

Subscription 是另一条路径。一个 Ticket 创建之后，它会订阅若干 Thread（它自己的 Thread + 可能的 PR Thread）。这个 Thread 上的任何新 Trigger——不管是人发的还是 bot/CI 发的——都会扇入给这个 Ticket，作为它的 Input。

但 Subscription 不加权。它不给 Ticket 新的 Mandate。Executor 收到 Input 后，如果它超出了当前 Mandate 的 scope，就 hand back（交还给 Main Session 路由）。

这就解决了一个经典问题：一个 PR 创建之后，后续所有评论和 CI 结果自动传到 agent，不用人每次 @ 它。但 agent 不会因为"有人在这个 Thread 说话"就被允许扩大 scope。

还有一个细节值得记：不同 Source 的身份从不互相映射。github.com 的 @alice 和 feishu 上的"Alice Wang"是两个身份。如果要在 prompt 里对应，那是 agent 的知识，不是域模型的规则。这避免了一个巨大的复杂性来源。

4

Ticket 状态机：六个互斥 stage

003 文档里的 Ticket stages 表，我觉得是整个项目最值得抄的一张图。

图 4 · 六个互斥、可机器判定的 Ticket stage

六个 stage，判定顺序从上到下，第一个匹配的行获胜。每一行的条件都是结构化事实。

person/answer：Ticket 有 Attention，等待人回答。person/review：最新 Report 是 ready，等人 review。person/blocked：Report 是 blocked 或 failed，且之后没人发消息。working/queued：没有 Assignment，或 Assignment 还是 pending。working：其他情况。idle：Report 是 waiting，或者 Assignment 已结束。

Ticket stage 不跟随 Executor Session。这是刻意的设计。一个 Ticket 可以 handoff 给另一个 Executor，也可以被 resume（idle 状态下收到新 Trigger 或人发消息自动恢复），Executor Session 只是执行器，Ticket 的状态自己决定。

person/stop 是独立出口——人显式停止一个 Ticket 时，Mandate 被撤销，Subscription 被丢弃，之后这个 Thread 上再发什么消息都不会回到这个 Ticket。这和 blocked/failed 的 resume 路径不同。

Execution 层还有一个我觉得很聪明的点：Executor Session 里的前台 shell 命令 5 秒后自动转到后台。这样 worker 在等待 npm install 跑完时，已经在下一个 step 了，不会卡住整个会话。

5

Engine + Port 解耦

架构上 dsh-superagent 也挺克制。Runtime 只是装配根，不含域规则。Engine 自己构建内部 parts，是所有域规则的唯一中心。Executor 和 Assessor 通过回调接口回到 Engine。

图 5 · Engine 是大脑，Runtime 只负责装配

Engine 周围是五个 port：Store（Repositories）、Policy（版本化规则）、Assessor（Eval 研判）、Executor（执行交付）、Outbox（输出事件）。Source plugins、Session tools、Management routes 都是外部 glue，翻译 Source payload、HTTP 请求、Harness 事件成 Engine 能懂的调用。

所有 Effect（执行副作用，包括持久化 store 事件、通知 Executor、通知 Session、发 Outbox 消息）统一进 Effects 队列异步执行。Engine 不直接触发副作用。

这个结构的好处很直接：你想换 Session executor，只需要换 Executor port 的实现。你想把 Store 从内存换成 Postgres，只换 Store port。Engine 不动。

6

给想自己搭 super agent 的七条启发

我觉得 dsh-superagent 最有价值的地方是"反框架"。它故意不做一个大而全的 framework，而是让你从一份极简的域模型开始。

一、先定域模型，再写代码。域模型里先写 Rejected concepts

dsh-superagent 的域模型里，我最喜欢的不是七个概念本身，是那个 11 行拒绝理由的表。每一条都在告诉你：这个概念想出来过，但我们把它砍掉了，原因是……写代码之前先写这样一张表，能帮你避开 80% 的架构膨胀。

二、把"授权"和"上下文"分开

Mandate 管授权范围，Subscription 管上下文注入。这是 dsh-superagent 整个设计里最精妙的一刀。Agent 看到的每条输入都经过这两层过滤：我有没有权利处理这件事（Mandate），以及我现在知道什么（Subscription）。

三、Ticket 自己定义状态，不跟随 Session

这让 Ticket 可以 handoff、可以 resume、可以多 Executor 接力跑完。如果 Ticket state 绑定在 Session 上，就会被 Session 生命周期卡死。

四、所有状态判定必须是结构化事实

不能从 agent 的自然语言报告里推断"它是不是在等我"。必须让 Executor 通过结构化字段上报（Attention / Report 的 ready / blocked / failed / waiting）。这样 Panel 才能可靠展示"需要人做什么"，不会被 agent 胡说八道。

五、Policy 版本化，改规则不 revoke 正在跑的 Mandate

Policy 变了，把变更 delivery 给 Assignment，但不取消正在跑的 Ticket。因为"半完成的工作被突然取消比留着它更贵"。Mandate 只在 person stop 时被撤销。

六、不同 Source 的身份永不互相映射

这是刻意不做的事。一旦要做跨平台身份映射，你就进入了账号体系、同步、冲突解决这些无限复杂的领域。dsh-superagent 选择让 agent 通过 prompt 知识自己识别"这两个账号是同一个人"。

七、设计约束必须能被面板展示出来

Panel 的三个问题（需要我什么、系统健康吗、一件事的来龙去脉）直接映射域模型里的概念（Ticket、Source、Trigger、Eval、Execution）。Panel 不是给运营看的 dashboard，是给操作员看的状态机。

 

最后一个我觉得值得记的细节：Trigger 被 Source 过滤掉（比如是 bot 自己发的消息），之后会被丢。它不会进入 Eval、不会留下 Trace。但如果你后面需要，Panel 里能看到它被 drop 了，还能点进去看为什么。

这就是 dsh-superagent 做对了的事：它让 agent 的"沉默"也被看见。

 

DeerFlow 给你的是一条能跑起来的流水线。dsh-superagent 给你的是一份写好的域模型。

 

如果你准备自己搭 super agent，先读 dsh-superagent 的 001 域模型文档。里面那张被拒绝概念的表，比任何 framework 文档都能帮你少长十倍的冗余。

然后跑起来 DeerFlow 看看 harness 层怎么落地。

先想清楚域模型，再选框架。
